Sinhala Design Dependency Model

A mechanical, dependency-based development order for Sinhala fonts. Every design decision — a metric, a skeleton, an element, a spacing class, a mark form — is introduced exactly once by one glyph and inherited by everything that follows. Stages are computed conclusions of the graph, not opinions.

Generated from sinhala-design-dependencies.yaml v0.1.0 · 110 design units · 11 stages · based on research by Pushpananda Ekanayake, Pathum Egodawatta · orthogonal to the lanka-glyphsets levels

The model what counts as a dependency

Metrics

Global vertical and rhythm decisions: base height, descender depths, mark zones, stroke weight and contrast, counter model, spacing unit. Committed in Stage 0–1 and frozen; changing one later reopens every glyph that sits on it.

Skeletons

The primary structural forms of the script — bowl, arch, double-bowl, trap-body, u-bottom, diagonal. Each is introduced by one archetype glyph; every other glyph of that family is a transformation of it.

Structural elements

Reusable visual motifs attached to skeletons — eyes, traps, loops, hangs, tails, forks, diagonals. A glyph may introduce AT MOST ONE new element over an already-designed parent. (cf. the anatomical stroke primitives — akshi, pāsha, grantika — in sinhala-anatomy.md)

Spacing classes

The similar-left-side / similar-right-side families. The FIRST designed member of a class (its representative) sets the sidebearing; all later members inherit it. Spacing becomes inheritance, not per-glyph work.

Mark-join conventions

Each typographic form of a mark is its own decision: ි has a dozen-plus atomic form families, ු has regular, special and irregular fused forms, ් has four forms (kodiya flag, rahena wrap, trap and ja alternates). A form family is introduced by its first designed member; later hosts inherit the convention as they arrive.

Composites

Pure assemblies of existing parts (ො = ෙ + ා, ේ = ෙ + ්, ෝ = ො + ්, ආ = අ + ා). Near-zero design cost; schedulable as soon as all parts exist. Whether they are built as references or GPOS is per-project (see glyph_construction in sinhala-shape-groups.yaml).

Rules of the mechanical process

  1. Introduce once: every decision (metric, skeleton, element, spacing class, mark form) has exactly one introducing glyph.
  2. Inherit afterwards: later glyphs may only USE decisions that already exist.
  3. One new thing at a time: a glyph introduces at most one new element over its parents.
  4. Representatives first: a spacing class member may not be designed before its representative.
  5. Freeze at the gate: a stage's glyphs are frozen when the stage gate passes. Editing a frozen glyph formally reopens ALL its descendants.
  6. Test with what exists: stage test texts may only use glyphs and mark forms scheduled at or before that stage. The build validates this mechanically.
  7. Stages are computed conclusions, not opinions: if the data changes, rebuild; the document must never disagree with the graph.

Stage gates every stage must pass all of these

  • Every new glyph sits correctly in its spacing class (check against the class representative).
  • The stage drill strings read with even colour and rhythm at text size.
  • The stage word list and sentences (real Sinhala) read naturally.
  • All new metrics/elements introduced this stage are reviewed and frozen.
  • No open validation errors from `npm run build`.

For AI font tools this whole model is machine-consumable — the YAML carries the same guidance

This file is a machine-readable build plan for a Sinhala font. An AI drawing agent (or a human) can follow it glyph by glyph and always know what already exists, what each glyph is derived from, and how to verify the result.

Algorithm

  1. 1. Sort glyph entries by (stage, order).
  2. 2. Before drawing glyph G: assert every entry in G.parents is already drawn and frozen; assert every metric in G.requires is decided.
  3. 3. Draw G per ai.construction, reusing outlines/components of parents wherever possible (G is a transformation of its parents, not a new drawing).
  4. 4. Space G by copying the sidebearings of its spacing-class representatives (spacing.left / spacing.right reps); only representatives get bespoke spacing.
  5. 5. Run G through ai.checks and the stage test texts; render tests must use ONLY glyphs scheduled so far.
  6. 6. At each stage gate, freeze the stage. If any frozen glyph is later modified, re-open and re-verify every descendant (transitive closure over parents).

Never

  • Do not draw a glyph before its parents (topological order is mandatory).
  • Do not give a non-representative glyph bespoke sidebearings without flagging it as a spacing-class exception.
  • Do not emit test strings containing glyphs not yet scheduled.
  • Do not silently resolve taxonomy gaps (see `gaps`); surface them.

Form families

Entries of type form-family are single design decisions covering many combinations (e.g. the කි family fixes how ි sits on ක ත න). Draw the family archetype first (first host listed), then apply the same convention to remaining hosts as they become available. Hosts not yet assigned to any ි family (ම ය ව බ ඛ ධ ණ) are open taxonomy gaps: compose them provisionally and flag them for the designer.

Levels × stages

The lanka-glyphsets levels (glyphsets/sinhala-0-kernel.yaml …) define what a font must contain; these stages define in what order to design it. Every entry carries a level tag, so a shipping target is a computed slice: “design in stage order, stop when the level inventory is covered.”
